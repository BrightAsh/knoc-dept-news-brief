# 분석 파이프라인

목표는 기사 전체를 막연히 부서에 넣는 것이 아니라, 한국석유공사와 각 부서가 실제로 봐야 할 기사와 근거 문장/문단을 찾는 것입니다.

## 핵심 원칙

- 0차 키워드는 최종 판단이 아니라 A/B 라우팅입니다.
- 최종 관련성 판단과 부서 배정은 LLM이 한국석유공사의 역할, 22개 부서 역할, 기사 문맥을 함께 보고 수행합니다.
- 1차는 누락 방지가 우선이고, 2차는 최종 정확도가 우선입니다.
- 기사 하나가 여러 부서에 배정될 수 있습니다.
- 긴 기사 중 일부 문장/문단만 특정 부서와 관련되면 해당 문장/문단을 근거로 저장합니다.

## 0차: 키워드 라우팅

파일: `config/stage0-keywords.json`

입력 기사에서 `한국석유공사`, `석유`, `원유`, `석유비축`, `자원개발`, `공공기관` 같은 확실한 단어를 찾습니다.

결과:

- A 그룹: 키워드가 잡힌 기사
- B 그룹: 키워드가 잡히지 않은 기사

주의:

- A 그룹이라고 관련 기사로 확정하지 않습니다.
- B 그룹이라고 버리지 않습니다.
- 이 단계는 LLM 비용과 검토 전략을 나누기 위한 라우팅입니다.

출력: `data/YYYY-MM-DD/stage0.json`

## 1차: LLM 후보 검토

권장 모델: `llama-3.1-8b-instant`

1차는 모든 기사에 대해 넓게 판단합니다.

- A 그룹: 키워드가 실제 업무 관련성으로 이어지는지 검토
- B 그룹: 키워드가 없어도 문맥상 한국석유공사와 연결될 수 있는지 검토

결과:

- C 그룹: 1차 후보 기사
- D 그룹: 1차 제외 기사

1차 판단 기준:

- 애매하지만 후속 검토 가치가 있으면 C로 남깁니다.
- 부서 후보도 같이 배정하지만, 최종 배정은 2차에서 확정합니다.
- 이유와 근거 segment id를 남깁니다.

출력: `data/YYYY-MM-DD/stage1.json`

## 2차: LLM 최종 검토

권장 모델: `meta-llama/llama-4-scout-17b-16e-instruct`

2차는 더 많은 본문 문단을 넣고 최종 판단합니다.

- C 그룹: 1차 후보의 이유와 부서 배정을 정밀 검토
- D 그룹: 1차에서 제외됐지만 놓쳤을 가능성을 본문 기반으로 재검토

결과:

- 최종 포함/제외
- 최종 관련 이유
- 최종 부서 배정
- 부서별 근거 문장/문단/기사 단위

출력: `data/YYYY-MM-DD/stage2.json`

## UI 최종 출력

`scripts/analyze.mjs`는 2차 결과를 기반으로 `briefs.json`을 만듭니다.

```text
briefs.json
  overall      전체 관련 기사
  departments  부서별 기사와 근거
  pipeline     0차/1차/2차 요약
  llm_review   UI 호환용 LLM 상태
```

UI는 `briefs.json`만 읽으면 됩니다. 중간 단계 파일은 검토와 디버깅용입니다.

## 모델 교체 포인트

모델은 코드에 고정하지 않고 GitHub Actions variables로 교체합니다.

```text
STAGE1_PROVIDER
STAGE1_MODEL
STAGE2_PROVIDER
STAGE2_MODEL
```

현재 지원 provider:

- `groq`
- `github-models`
- `ollama`
- `openai-compatible`

운영 기본값은 Groq의 Llama 모델입니다. 비용을 쓰지 않으려면 결제 설정을 추가하지 말고 무료 한도 안에서만 사용합니다.
